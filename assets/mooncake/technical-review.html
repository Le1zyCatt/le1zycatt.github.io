Mooncake 总体架构：关键模块与本次修改落点

01

UB 接入 TENT：从兼容层到 Native 数据面

第一阶段目标是低风险接入：TENT 能识别和选择 UB，但真正的数据面仍复用 Classic Transfer Engine。 下一阶段则消除中间模型转换，让 UB 成为真正的 TENT-native transport。
架构演进 复用 URMA 控制面 / 数据面解耦 消除 Classic TE 依赖

非 Native 版本

  • TENT 负责 Transport 加载、选择、控制面和 UB bootstrap。
  • UbTentTransport 将 TENT Request / Metadata 转换为 Classic TE 模型。
  • 内存注册、切片、设备选择、Endpoint 与 URMA 数据面仍由 Classic UbTransport 执行。

Native 版本

  • TENT Request 直接生成 UbTask / UbSlice，不再转换成 Classic TransferRequest。
  • UbWorkers 负责切片执行、路径选择、提交与完成处理。
  • 通过 UrmaAdapter 直接对接 liburma，UB 数据面完整归入 TENT。

02

Warmup：把首次建链成本移出业务热路径

问题不在单次握手有多慢，而在冷启动时大量 GET/WRITE 同时发现“没有可复用连接”，于是把 metadata、 socket handshake 和 endpoint 创建集中压到同一个时间窗口，形成连接风暴。
主动预热 有界目标数 复用原 TE handshake 消除业务首访突发
关键定义： Warmup 不是 KV 数据预加载，而是通过一次真实的小型 READ-only probe，提前走完 remote metadata → handshake → endpoint → transfer 的初始化路径。

没有 Warmup

  • 第一批业务请求同时触发 openSegment / metadata 查询。
  • 多个请求并发进入 socket handshake。
  • listener / worker / 状态轮询被短时间突发放大。
  • 结果体现为尾延迟、超时，极端情况下出现 hang / fail。

加入 Warmup

  • Client 初始化阶段先向 Master 获取有限数量目标。
  • 对目标执行 READ-only probe，建立并缓存 transport endpoint。
  • 资源清理与状态查询异步完成，避免影响真实请求。
  • 业务流量到来后直接复用已建连接。

RDMA 少一跳：从 Requester Pull 改为 Target Push

远端 SSD read 原方案要求 Target 先读到 staging buffer，再把 staging 地址返回给 Requester， 由 Requester 发 RDMA READ 拉取，最后还要释放 staging buffer。优化思路是让 Requester 一开始就暴露目标 buffer， Target 读完 SSD 后直接 RDMA WRITE。

CI：什么时候触发，哪些状态必须关注

触发方式

打开 PR创建 PR 后 GitHub Actions 按仓库的 pull_request / workflow 条件启动。
Push 新 commitPR 分支更新会触发新的 checks；我们多次通过这种方式验证修复后的 CI。
Rebase / Sync只要产生新的 HEAD，同样会重新跑对应工作流。
改 CI 文件如果修改 .github/workflows/*，除了 CI 自身通过，还可能额外触发 .github 的 CODEOWNER 审批要求。

我们实际遇到的 Native UB CI

Build & Test (Linux) └─ tent-ci (ub-mock) ├─ Configure project with TENT ✅ ├─ Build project with TENT ✅ ├─ Test (TENT) ✅ └─ CI Gate ✅

这证明的是 mock UB 构建、链接、TENT 单测和 CI matrix 正常，不等价于真实 UB 网卡、liburma 双节点数据传输已经验证。

Check / 状态应该如何判断处理原则
Build & Test / relevant matrix 需要通过 与本次改动相关的构建和测试 job 是最基本的合入门槛。
CI Gate / Required checks 需要通过 最终以 PR merge box / Required 标记为准；Required 失败不能当作“环境问题”直接忽略。
format / pre-commit / codespell 应通过 尽量本地提前解决，避免把纯格式问题留给 CI。
Qoder Review = skipped 不需要变成 success 我们遇到的 fork / cross-repo PR 中 Qoder 会被设计为 skipped；skipped 本身不是 CI failure。
条件不匹配的 matrix job = skipped 正常 平台、路径或 feature 条件未命中时可以跳过，不能把 skipped 与 failed 混为一谈。
Codecov / 外部分析 看是否 Required 覆盖率是重要质量信号，但是否阻塞合并取决于仓库当时的 Required 配置；不能只看颜色判断。
CI 判断原则： 不要问“是不是所有绿色都必须有”。真正的判断顺序是：先看该 check 是否与本次改动相关，再看它是否被仓库标记为 Required，最后看失败日志属于代码、测试、环境还是条件配置。

CODEOWNERS：谁应该 Review

CODEOWNERS 是什么

仓库用路径规则把代码目录映射到负责维护的人。PR 修改某个受保护目录后，GitHub 可以自动请求相应 owner review，并在 branch protection 下要求 owner approval。

仓库中搜索： .github/CODEOWNERS CODEOWNERS docs/CODEOWNERS 典型形式： /mooncake-store/ @... /mooncake-transfer-engine/tent/ @... .github/ @...

怎么决定 @ 谁

第一优先PR 右侧 GitHub 自动请求的 Reviewers / Pending CODEOWNERS。
第二优先查看 .github/CODEOWNERS，按实际修改目录定位 owner。
第三优先看近期同模块 PR 中真正 review / merge 过的人。
不要做不要一次性 @ 大量无关 maintainer；已经 Approve 的 reviewer 不需要重复催。
我们遇到过的典型情况： 修改 TENT 代码需要 TENT owner；修改 Store 代码优先找 Store owner；如果同时修改 .github/workflows/ci.yml，即使代码 reviewer 已经 Approve，也可能因为 .github 路径本身需要额外 CODEOWNER approval 而暂时无法合并。

Bot Review

  • 适合发现格式、边界条件、潜在生命周期、测试覆盖等问题。
  • 不能因为是 bot 就全部接受，也不能因为是 bot 就忽略。
  • 先验证它指出的问题是否真的能沿代码路径发生，再决定修还是解释。
  • 如果修复，最好用 regression test 证明问题确实被封住。

Maintainer Review

  • 更关注模块边界、公共接口、长期维护成本和 PR scope。
  • 设计方向被质疑时，不应只局部改代码；需要先确认 maintainer 想要的架构边界。
  • 每个 comment 修复后回复“改了什么 + 为什么这样改 + 测试结果”。
  • 过时 thread 即使代码已更新，也应确认是否需要手动 Resolve，避免 merge rule 阻塞。

当前 PR 模板中的硬性自检项： 自审、运行 ./scripts/code_format.sh、运行 pre-commit run --all-files、必要时更新文档、补充能够证明修改有效的测试；如果改动超过 500 LOC，模板要求先提交 RFC Issue。

提交前 · 代码

无无关 diff；接口命名、错误处理、资源释放与社区已有风格一致；大块临时代码不直接进入 PR。

提交前 · 文档

Issue、PR、代码行为三者一致；不要让 PR 描述停留在旧设计；Module 只勾实际改到的模块。

提交前 · Reviewability

Reviewer 能从 PR 描述快速回答：为什么改、数据路径怎么变、风险在哪里、如何验证、哪些还没验证。

技术实现与社区协作的共同主线

技术工作分散在 transport、Store、cache 和 allocation，社区工作覆盖 Issue、CI、Review 与测试；二者共同目标都是让变化可理解、可验证、可维护。
